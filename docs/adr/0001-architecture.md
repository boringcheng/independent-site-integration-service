# ADR-0001：以 MySQL 任务表作为调度的权威源

- 状态：Accepted
- 日期：2026-11-13
- 决策者：项目维护者
- 相关里程碑：M1 / M2

## 背景

独立站集成服务要同时处理几十家店铺的同步任务：库存、商品、订单、Webhook 事件。
真正难的不是调用平台 API，而是：

1. 同一家店铺的任务必须按顺序执行（初始化没完成就同步库存 = 数据灾难）；
2. 不同店铺之间要能并行，否则一家慢店拖死全部；
3. Worker 会崩溃、会网络超时，任务不能丢，也不能重复产生副作用；
4. 大任务要能拆片并行，失败只重试一片。

## 决策

**用 MySQL 的 `shop_task_queue` 表保存任务顺序与状态，作为唯一权威源。**

具体展开：

1. **一店铺一队首**：任务行按自增 `id` 排序，同店串行、跨店并行；
2. **执行权 = 租约**：`lease_token` + `lease_expires_at` + `run_epoch` 写在任务行上；
3. **栅栏提交**：完成/失败都必须带 `lease_token` 与 `run_epoch` 条件更新，
   租约被接管后旧执行者的写入自动失效；
4. **不变量下沉到数据库**：用生成列 `active_shop_id`（RUNNING 时 = shop_id，否则 NULL）
   加唯一索引，从数据库层面禁止"同一店铺两个 RUNNING 任务"；
5. **隔离级别固定 READ COMMITTED**：领取逻辑依赖"拿到行锁后重新读能看到最新提交"。

## 为什么不选其它方案

| 方案 | 为什么不用 |
| --- | --- |
| Redis 分布式锁控制店铺顺序 | 锁与业务状态分离，进程崩溃后锁与任务状态可能不一致；无法用一条 SQL 审计"谁在跑" |
| 只用 Celery 队列顺序 | Celery 是投递与执行框架，不保证同店顺序；重试、抢占、可见性语义与业务状态不同步 |
| `SELECT ... FOR UPDATE` 锁 `shops` 主表 | 任务创建/序号分配会与店铺主数据产生锁耦合，高频时成为瓶颈 |
| 应用层"先查再改"保证唯一 RUNNING | 两个事务可能都查到"没有 RUNNING"，存在并发窗口，必须靠数据库约束兜底 |

## 后果

正面：

- 任务状态、执行权、顺序在同一事务里，崩溃后可通过租约回收；
- 可以直接用 SQL 审计任何店铺的队列与执行历史；
- 分片作业可以在同一套状态机上扩展。

代价与缓解：

- 调度依赖数据库轮询，高频时对 MySQL 有压力 → 用索引 `(shop_id, status, id)` 与
  `(status, available_at)`，并控制扫描批量；
- 租约时长需要大于单任务最长执行时间 → 长任务必须续租（`renew_lease`），
  否则会被误判为过期；
- READ COMMITTED 不是 MySQL 默认值 → 连接工厂统一设置，测试断言隔离级别。

## 后续

- M2 落地 `claim / renew / complete / fail / reap`；
- M3 落地分片作业的 Barrier + Publish；
- 如果未来店铺规模超过单库承载，再评估按 shop_id 分库，本 ADR 需要重写。
